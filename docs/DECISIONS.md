# Decisions log

| 2026-10-09 | **Animations are tagged by mapping id**, not clip file, with optional per-rig overrides; if a rig has no clip for a tag, its DFLT clip of the same category and phase is used (logged). Tags come from the in-game browser (`!dag_animlib`, `DarkAndGate/anim-tags.txt`), are made permanent in `data/anim_tags.lua`, and Swing / Jump read them before the automatic picks. | Picking clips by filename kept going wrong (wrong phase, wrong rig, one clip under ~50 ids); mapping ids resolve per character through its own AnimationSet, which is what custom characters need. |
| 2026-10-09 | **Animation speed goes through the Genome `PlayRate` blueprint variable** when the character's blueprint has it (learned from QSAT, credited; own code). No Ghidra `SetAnimPlaySpeed` hunt. If gameplay blueprints lack the variable, choose between our own blueprint edit / an optional dependency / asking the author / the native socket route before building. ([anim-speed.md](spikes/anim-speed.md)) | QSAT shows the lever is Lua-reachable on photo-mode dummies; whether it is on gameplay characters is one probe away. |
| 2026-10-09 | Jump clip ids (BG3 JumpFlight animation-mapping ids, stance-independent) live in `data/movement.lua`; no animation scan at load (`!dag_jump_anim_scan` on demand). The server clears the Osiris queue before **every** scripted clip. | The scan took ~4 min, so early jumps had no animation; the first swing clip after a pause only played on the second click (the second click's queue purge released it). |
| 2026-10-09 | **Character hitboxes are vertical cylinders** (`data/hitbox.lua`: r 0.35 m, h 1.8 m; zones by height fraction: head >= 0.85, torso >= 0.45, else limbs). A jumping character's cylinder rises with its visual lift (`Shared/Hitbox.lua`; server learns jumps via `DAG_JumpStart`, other clients via `DAG_JumpNotify`). Client aim and server hit validation both use it; reach is measured to the cylinder surface. | Developer asked for hitboxes that jump with the player; precision beyond a cylinder isn't needed. |
| 2026-10-09 | **Server clears the character's Osiris queue before every scripted animation** and once more after the last clip should have ended (watchdog). Swings now honour `recovery_ms` (one early click is buffered). | `Osi.PlayAnimation` is a queued Osiris task; LMB spam queued clips behind a playing one and left Gale unable to walk until a reload (reproducible with 3 fast clicks). |
| 2026-10-09 | Jump airtime stays data-driven (`clip_air_s 0.80 x duration_mult 1.60 = 1.28 s`); BG3's JumpFlight clips (Ascend, Falling, Descend, Recover) are fitted into it. | Playtest: 1.28 s "feels good". |
| 2026-10-09 | **Space = floaty straight-up jump, visual only.** The DLL lifts the local body (vtable hook on the player Visual's SetWorldTranslate/SetWorldTransform, slots 2/5/6) and the camera along `y = h·(1 − |2u − 1|^k)`; the character's real position never leaves the ground, so a jump doesn't clear obstacles. Tuning in `data/movement.lua` (`duration_mult`, `height_m`, `apex_flatness`), live via `!dag_jump`. Fallback if the vtable check fails: camera-only lift. Other players see the jump animation but not the lift (co-op lift is M6 work). ([m1b-visual-lift.md](spikes/m1b-visual-lift.md)) | Writing the server transform each tick fights physics and pathing; BG3's Jump spell can't be made floaty or tunable. |
| 2026-10-09 | **Jump animation = BG3's jump clips played in phases** (start, loop re-triggered through the hang, land timed to touchdown), not slowed. ([m1b-anim-speed.md](spikes/m1b-anim-speed.md)) | No reachable native speed lever: Granny control speed exists but Larian samples through Genome clocks. A Genome `PlayRate` variable may be writable from Lua; `!dag_anim_vars` probes it. |
| 2026-10-09 | **FP camera anchors on the head bone** (`Head_M` from the skeleton's live Granny world pose), with the eye height above the bone calibrated from the signed-off pivot eye at rest, so the default view height doesn't change. `!dag_pov_anchor pivot` restores the M1a camera. ([m1b-head-bone.md](spikes/m1b-head-bone.md)) | Attack animations and the jump move the body away from the engine pivot; the world pose gives the bone position directly, with no bind pose or bone map needed. |
| 2026-10-08 | **M1a closed; bone reads, anim speed/cancel and ragdoll push archived.** M1b hit detection uses a timed camera-relative swing arc (ray fan from the eye) instead of weapon-bone sweeps; hit stop deferred (no anim-speed API). See ROADMAP § Archived (future). | Pose arrays reach Lua but need a bind-pose + bone-map pass before they yield world positions. The ray-fan swing is tight enough for the M1b feel and unblocks the combat vertical slice. Anim-speed is still Lua-unreachable; hit stop is polish. |
| 2026-10-08 | **First-person camera = NCT placement + DLL commit override, toggled with `!dag_full_pov`.** The DLL sets eye and look-at together inside the `vt[0x58]` commit and restores the camera fields after; anchor is the engine's desired camera point; MMB toggles mouse-look through an SDL event filter | Verified in-game: no lag, yaw + pitch, head hidden, dialogue/cutscenes untouched. Every earlier attempt that wrote camera fields outside the commit (post-chain pin, instant_follow damping writes) either didn't reach the screen or broke it. |
| 2026-10-08 | Keep POV defaults `eye_fwd 0.10`, `down_fwd 0.20` (eye slides forward up to 20 cm as you look straight down), `pivot_up -0.15`, look distance 1.0 m | Playtested: 0.20 fully hides the neck opening when looking down. |
| 2026-10-08 | Head-bone anchor deferred inside M1a: pose arrays are 3x4 model-space skinning matrices, not bone positions | Needs bind-pose positions and a skeleton-to-binding bone map before it can drive the camera; the engine-anchor camera already plays well, so this is polish (head bob, leaning), not a blocker for M1b. |

| 2026-10-08 | **AI melee goes through our swing and blade-path system, not BG3 attack rolls** (M1 scope note) | Brawl's AI calls `Osi.UseSpell` for melee, which triggers BG3's attack-roll pipeline. That contradicts our "every hit is aimed" pillar. In M1b, `Pick.decideActionOnTarget` is adapted so melee choices resolve through our swing scheduler + blade-path hit check; only aimed attack rolls (projectile spells with saves) still hit the Osiris path. |
| 2026-10-08 | Native plugin scope grows: add `SetAnimPlaySpeed(entity, mult)` and `CancelAnim(entity)` ([spike 4](spikes/04-anim-control.md)) | AnimationSetComponent and AnimationBlueprintComponent don't expose any playback-speed field (`PlaySpeed`, `Speed`, `Rate`, `TimeScale`, `PlaybackRate` all return "property does not exist"). | 2026-10-08 | `data/` tuning files are Lua tables (`return { ... }` modules loaded via `Ext.Require`) | SE Lua is already the runtime, so no parser or dependency is needed; comments and arithmetic expressions make tuning numbers readable; MCM reads/writes the same shape at runtime. Only reason to pick JSON/TOML would be external tooling that can't parse Lua — we don't have any. If one appears later, a `data/export-to-json.lua` script is a 20-line fix. |
| 2026-10-08 | Native plugin also owns always-on mouselook: hook the input/camera update, read mouse delta, write yaw/pitch on the camera controller each frame | SE exposes `KeyInput`, `MouseButtonInput`, `MouseWheelInput` but no mouse-motion event (`ViewMousePosition` is in `UI.h` but not Lua-bound). Lua-only FPS-style mouselook is not achievable. The native plugin's camera update hook is the right home — same hook already needed for camera follow (spike 11) and bone reads (spike 3). |
| 2026-10-08 | Impact feedback uses directional death animations, not a physics-impulse ragdoll push ([spike 6](spikes/06-ragdoll-direction.md)) | Lua can ragdoll via `Osi.ApplyStatus("KNOCKED_DOWN")`, but no API accepts a push vector. | 2026-10-08 | Spell casts from script go through `Osi.UseSpell(caster, spell, target)` — no action economy or spell-list validation to work around ([spike 5](spikes/05-spellcast-from-script.md)) | Verified in-game: lvl 1 Gale cast Fireball with no action spent, no slot spent, no prep requirement.
